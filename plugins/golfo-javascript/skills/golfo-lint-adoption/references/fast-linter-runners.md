# Running the golfo-lint preset faster than ESLint

The ESLint preset (`createEslintConfig`) stays the single source of truth for every runner. The adopted runner is **`bun lint`** (Bun canary until it ships in a stable release; then pin the stable version). An oxlint config generated from the preset was built, measured and dropped — keep its lessons below only for evaluating other runners.

## bun lint (adopted)

1. Consumer `eslint.config.mjs`: `createEslintConfig({ tsconfigRootDir: import.meta.dirname, linter: "bun", react, next, vitest })` spread with the repo's project-only overrides (import restrictions). `linter: "bun"` swaps `golfo-lint/no-unnecessary-condition` for the native `@typescript-eslint/no-unnecessary-condition`: bun runs plugin rules in JavaScript without type info, and a typed JS rule makes the run exit 2 ("rules that run in JavaScript cannot use type information") unless `--allow-unsupported`.
2. Script: `"lint": "golfo-lint lint"` (wraps `bun lint --no-script --type-aware -f json` + the post-filter below, forwards extra args like `--fix` or files; also part of `golfo-lint all`). Running bare `bun lint` shows the unfiltered native reports. If you ever call `bun lint` from a `lint` script, `--no-script` is mandatory: without it `bun lint` runs the project's `lint` script, i.e. itself.
3. Tests tsconfig: typed rules use each file's nearest `tsconfig.json`; if the root one excludes `tests/**`, add `tests/tsconfig.json` (`"extends": "../tsconfig.test.json"`, `"include": ["**/*.ts", "**/*.tsx"]` — includes are relative to the extending file) or tests resolve to `any` and produce hundreds of `restrict-plus-operands`/`no-unnecessary-type-assertion` false positives.
4. CI: `oven-sh/setup-bun` (by SHA) with `bun-version: canary` (or `.bun-version` = `canary`) until the stable release; then pin it. Install it in every workflow that runs the script, `release.yml` included.
5. Remove what the runner replaces: oxlint configs/deps, `oxlint-tsgolint`, throwaway ESLint configs, the `lint:eslint` script and the ESLint cache steps in CI.
6. Verify: `bun lint --no-script -c <config> --doctor` (native vs JavaScript rules per plugin, removable packages), then `bun lint --no-script -c <config> --type-aware -f json -o <C:/... path>` and diff per rule against an ESLint JSON of the same code state.

Reference numbers, 3,100-file Next repo: ESLint 245–268 s (4 threads); oxlint generated config 77 s (sonarjs trimmed) / 136 s (full); **`bun lint --type-aware` ~47 s** with the same findings as ESLint (oxlint missed ~140: `no-meaningless-void-operator`, `no-unused-vars` on `_x`, `no-useless-assignment`, rules it does not implement).

## Typed custom rules under bun lint: native rule + golfo-lint post-filter

When a preset rule is a typed wrapper (e.g. `golfo-lint/no-unnecessary-condition` drops false positives of `@typescript-eslint/no-unnecessary-condition`), do not keep ESLint for it (one typed rule alone still took ~103 s with 4 threads: the TS 6 program build is the cost) and do not enable the native rule unfiltered. Run the native rule in `bun lint` (~3 s alone) and drop its unreliable reports from the JSON in golfo-lint, like the react-doctor filter:

1. With `linter: "bun"` the preset enables the native rule; a `golfo-lint lint` command runs `bun lint --no-script --type-aware -f json -o <tmp>` plus the user's args, filters, prints, and sets the exit code.
2. The filter parses each reported file with `ts.createSourceFile` (no checker), maps `line/column/endLine/endColumn` to the node, picks the judged value by `messageId` (bun uses typescript-eslint's ids; `neverOptionalChain` points at the `?.` token, `noOverlapBooleanExpression` at the binary expression) and walks the chain links with syntactic stand-ins for the checker: property read re-checked after an `await`/call, `let`/`var` assigned anywhere besides its declaration, host global (`globals.browser` + `globalThis`/`window`/…) not declared in the file, element access / indexed-element variable when the nearest tsconfig lacks `noUncheckedIndexedAccess` (`ts.findConfigFile` + `ts.getParsedCommandLineOfConfigFile`).
3. Validate against ground truth before wiring it: run ESLint once with only the typed wrapper rule (throwaway config importing `typescript-eslint` via `createRequire(<golfo-lint>/package.json)` because the consumer does not depend on it) and the native rule through `bun lint` on the same code, then a script that keys reports by `file:line:col:messageId` and counts kept∩truth, kept-not-in-truth (new false positives) and dropped∩truth (lost findings). Target: no new false positives; a few lost findings are acceptable.

Pitfalls:
- `bun lint` may report only the property name (`aborted` in `signal.aborted`): widen to the parent `PropertyAccessExpression` before analyzing.
- **`let`/`var`: "reassigned somewhere" alone over-drops** (a `let pool: Pool` assigned in `beforeAll` and checked in `afterAll` is a real finding). Treat it as stale-narrowing only when it is reassigned somewhere AND narrowed before the read: declaration with a type annotation + initializer or a literal initializer (counts from any function — TS ≥5.4 keeps declaration narrowing inside later closures), or, in the same function, an earlier check or literal assignment. Walk earlier occurrences in order: a non-literal assignment (`x = await read()`) resets to the declared type, so a later check is a real finding.
- **Unavoidable loss**: a truthiness check on a discriminated-union member (`if (!result.ok)` twice) looks syntactically identical to a mutable flag (`signal.aborted`); dropping it is the safe side. On TuTribu the final filter kept 182/183 ground-truth reports with 0 extra.
- When the user asks whether the dropped ones can be included, iterate the criteria against the ground-truth diff until only cases indistinguishable without types remain, and report those with the reason.
- A previous **read** of the same path does not narrow; only a previous check (if/while/ternary condition, `&&`/`||`/`??`, `===`/`!==`/`instanceof`, `!`, `typeof`) or an assignment does. Counting plain reads drops real findings such as `el.textContent?.` repeated in two assertions.
- Exceptions to "a non-literal assignment resets to the declared type": a `let` declared with a union annotation (`let item: Item | undefined; item = await load()`) is narrowed to the assigned type, so keep it as narrowed.
- Key member paths by static name, not syntax: `signal["aborted"]` and `signal.aborted` are the same path for the earlier-check search.
- Clamp report positions to the file (`getLineStarts()`): a file edited after `bun lint` read it makes `getPositionOfLineAndCharacter` throw a Debug Failure and takes the whole command down.

## Lessons that apply to any runner that runs ESLint plugins as JS

- **JS plugin rules get no type information.** Typed custom rules and many sonarjs rules either do not run or degrade; decide per rule whether a native typed equivalent exists and whether it brings back false positives the custom rule avoided.
- **Each JS-plugin rule costs its own time** (unlike ESLint, where typed rules share the TS checker and cutting them barely moves wall time). Trimming zero-finding JS rules pays off: measure with throwaway configs that spread the real one and filter rules, check they import before a long run (`node.exe -e "import('./x.mjs')"`), and bring the table to the user.
- **Compare on the same code state**: rerun the baseline after subagent fixes; an older JSON makes the new runner look like it misses or adds findings. Normalize rule ids before diffing (`typescript(x)` → `@typescript-eslint/x`).
- **A generated config for another runner drifts from the preset**: `@oxlint/migrate` skipped not-implemented/nursery rules, could not alias JS plugins whose name is native (renamed `unicorn-js/x` back to `unicorn/x`), passed settings as JSON (stripping `import-x/resolver-next`'s methods) and needed every plugin specifier resolved from `@golfo/lint` under pnpm. Prefer a runner that reads the ESLint config as is.
