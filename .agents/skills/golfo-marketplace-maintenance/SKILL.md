# Mantenimiento de golfo-marketplace / golfo-kit

Repo `golfo-marketplace` (suele estar en `~/ghq/projects/golfo-marketplace`): marketplace de skills para Claude Code, Codex y Hermes, con un plugin por ámbito (`golfo-kit`, `golfo-github`, `golfo-web`, `golfo-engineering`...; catálogo en el `README.md`). Leer primero su `AGENTS.md`: manda sobre esta skill. Donde esta skill dice `golfo-kit`, aplica igual al plugin que corresponda (el que contiene la skill tocada).

Esta skill vive en `.agents/skills/` del repo (Codex y Hermes la leen ahí; Claude Code por el symlink `.claude/skills/golfo-marketplace-maintenance`). No es parte de ningún plugin, así que no lleva bump de versión.

Reglas genéricas de PRs en paralelo y versionado: skill `parallel-pr-hygiene` (plugin `golfo-github`). Gotchas de Windows y Git Bash: skill `windows-git-bash-agent-gotchas` (plugin `golfo-kit`).

## Procedimiento para cambiar una skill

1. Un pedido concreto ("que la skill X siempre haga/use Y", "agregá Z a la skill X") NO es vago: no lo investigues a fondo ni preguntes antes. Chequeá solo los PRs abiertos que tocan esa skill y delegá enseguida, con el PR y el `codex-autofix-loop` ya pedidos en el prompt, porque el usuario corta la investigación previa para que lo hagas. El análisis fino (qué condicionales cambian) lo hace el hijo y lo justifica en el PR. Un pedido vago («mejorá la skill X») se aclara con UNA pregunta con opciones concretas: auditar primero (`/skill-optimizer mode=audit`), un cambio puntual, triggers o áreas nuevas. En la misma pregunta mencionar los PRs abiertos que tocan esa skill (`gh pr list` + `gh pr diff N --name-only`), porque van a conflictuar. En Discord, escribir las preguntas y opciones en el texto del mensaje, numeradas con letras (el usuario responde «1a 2b»): las opciones del `clarify` no se le ven ahí.
2. **Extender o crear otra skill.** Si el material nuevo comparte el flujo central de la skill (sus gates, su reporte, su cobertura), sumarlo como `references/<área>.md` más una fila en la tabla de ruteo. Separarlo en otra skill solo si un área necesita su propio procedimiento largo de «cómo arreglarlo»: esa skill es dueña del fix y la original conserva detección y medición, como `react-render-performance-patterns` junto a `measured-performance-optimization`. Dos skills con el mismo trigger compiten por la activación y parten el registro de cobertura. Cada referencia nueva, del tamaño de sus hermanas, linkeando a las skills dueñas de los temas vecinos en vez de repetirlos.
3. Worktree al lado de los demás: `git fetch origin && git worktree add -b feature/golfo-kit-<tema> ../golfo-marketplace-worktrees/<tema> origin/main`. `sibling-worktree` solo reusa ramas existentes. Esa rama queda trackeando `origin/main`: correr `git branch --unset-upstream` antes de `pnpm create-version` y pushear con `git push -u origin HEAD`, o el push va a `main`.
   - Hacer que una skill "siempre use" otra skill de golfo-kit: sumarla como paso explícito del Flujo y sacar los «si está disponible» y sus fallbacks, porque las dos viajan en el mismo plugin. No confundir esos condicionales con «si el proyecto no usa el kit» (código del kit en el repo consumidor): esa frase es otra decisión. El «cómo se hace» sigue en la skill dueña, sin copiar su procedimiento, y el eval nuevo tienta a resolverlo sin cargarla.
4. Cambios de skills: siempre por `/skill-creator`, con `evals/eval-config.json`, y cierre con `/skill-optimizer mode=audit` (reglas 1, 2 y 4 del `AGENTS.md`). Vale para CUALQUIER archivo bajo el directorio de una skill (`SKILL.md`, `references/`, `assets/`, `scripts/`, `evals/`), no solo para el `SKILL.md`: Codex marca como P1 el PR que lo saltea, aunque sea una línea en un asset. La única excepción es un cambio solo de metadata (`version`). Esas skills están en Claude Code: un agente que no las tiene (Hermes, Codex) delega el cambio en Claude Code DESDE EL PRINCIPIO (sesión interactiva con `--remote-control`, ver skill `claude-code`), en vez de hacerlo directo y delegar recién cuando Codex lo reclama, que cuesta una ronda de review.
   - Si el usuario dice explícitamente «no uses Claude Code, hacelo vos», Hermes hace el cambio directo PERO igual sigue `/skill-creator` y `/skill-optimizer` leyendo sus `SKILL.md`, porque reemplazarlos por chequeos a mano lo marca Codex como P1 («un pedido de no delegar no exime la regla»). skill-creator: `~/.claude/plugins/marketplaces/claude-plugins-official/plugins/skill-creator/skills/skill-creator/` → `python scripts/quick_validate.py <skill-dir>` (correrlo desde ese dir) + `run-evals --baseline` y puntuar las mismas assertions sobre `without-skill/<id>.txt` (campo `result` del JSON) para mostrar qué casos discriminan. skill-optimizer: `plugins/golfo-kit/skills/skill-optimizer/SKILL.md`, `mode=audit` es read-only y sin subagentes (Fase 1: contrato/invariantes/costo + formato de salida). `scripts/run_eval.py` (trigger evals) no está en esa instalación: dejar la activación como hallazgo abierto. Poner los resultados en las notas del PR. Una skill nueva también suma su entrada en `compatibility-report.json` (clonar la de una skill sin dependencias como `test-planning`, sumar `summary.total_skills` y `unverified` por agente; `json.dumps(indent=2, ensure_ascii=False)` reproduce el archivo byte a byte) y `pnpm compat:render`.
5. Cerrar enviado: commit, push, PR con `pr-description-template` (los hallazgos abiertos de la auditoría van en las notas para el revisor) y `codex-autofix-loop` lanzado sobre el PR, sin preguntar. Excepción: si existe `~/.work` en la máquina, no commitear, pushear ni abrir PR sin pedido explícito (ver `parallel-pr-hygiene`). Desde Hermes, el loop también lo corre la sesión delegada de Claude Code (modo nativo Monitor + cron), no el watcher de Hermes.

## Instrucciones para los repos que configura agent-ready-setup

Pedido típico: «agregá en AGENTS.md que…» (una directiva de comportamiento para los agentes de los repos consumidores).

El contenido que proyecta agent-ready-setup (rules, skills de stack, catálogo de profiles y el template de `AGENTS.md`) no vive en golfo-marketplace: vive en el pack oficial `guidomodarelli/golfo-agent-profiles`, con su propio `AGENTS.md` (reglas del repo y «Checking a Change»), su CI y releases por tag. El cambio va en un PR de ese repo y golfo-kit no se bumpea.

1. No tocar el template del bloque gestionado (`base/agents-template.md` del pack): el bloque solo lista rules vía `{{AGENT_READY_RULE_REFERENCES}}`, y una directiva suelta ahí rompe esa convención. La directiva va como bullet en la rule dueña del tema: `base/rules/` si aplica a cualquier repo, también sin código; `profiles/software-development/rules/` si aplica a cualquier repo de código; `stacks/<stack>/rules/` si es de un stack (copy y UI → `stacks/react/rules/react-style.md`, sección `User-facing copy`). Llega al `AGENTS.md` de cada repo según su configuración de updates: en el próximo sync si sigue `main` (el default) y con `agent-ready update golfo` si está fijado. Explicarle al usuario por qué quedó en la rule y no en el template.
2. Escribirla en inglés como sus hermanas, en imperativo y con las excepciones que evitan que el modelo la sobreaplique (p. ej. «menos texto en la UI» no borra `aria-label`, errores ni avisos de consecuencias irreversibles).
3. Versionar el cambio en el pack: subir `version` en `agent-ready-pack.json` y sumar su entrada en `changes`, con `breaking` si el consumidor tiene que actuar (regla 6 del `AGENTS.md` del pack; la CI falla si falta y, al mergear, publica el tag). Una rule no es una skill y no pasa por `/skill-creator` (regla 5); un cambio en una skill del pack sí, con sus evals y `/skill-optimizer mode=audit` (reglas 1, 2 y 4).
4. Correr los chequeos de «Checking a Change» del `AGENTS.md` del pack, con `--engine` apuntando a `plugins/golfo-agent-ready/skills/agent-ready-setup` de un checkout de golfo-marketplace en `origin/main`.
5. Revisar con `grep` si otra rule o skill del pack linkea la sección tocada (p. ej. `component-creation` aplica `User-facing copy`) y si una skill de golfo-kit nombra la rule (`error-observability-diagnostics` usa `react-security.md` y `upstream-contracts.md`): si ya la linkea, no hay que replicar nada; si la renombrás, actualizar esas referencias en los dos repos.
6. Una rule nueva que junta temas que ya tienen rule dueña (p. ej. `patterns-we-do-not-use.md`) lleva links en las dos direcciones, en el mismo PR: la rule nueva linkea a cada rule dueña, y cada rule dueña suma en su sección una línea que nombra el patrón y apunta a la rule nueva, sin repetir la alternativa, el motivo ni las excepciones. Sin ese link de vuelta, el agente que consulta la rule dueña (p. ej. `database.md` por una migración) no ve la prohibición. Si la rule dueña ya tiene una línea casi igual, sumarle un «See also» a esa línea: un bullet nuevo que repite la prohibición es contenido duplicado. Formato del link: «see `<Sección>` in `<rule>.md`», con el nombre del heading y no el de la entrada en negrita.

## Diseñar capacidades nuevas de agent-ready-setup

Pedidos típicos: «¿se puede hacer que agent-ready-setup tenga X? decime qué harías según lo que está hecho hoy» o «te hago varias preguntas y de cada una creá una issue». El entregable de la primera respuesta es un diagnóstico («ya existe / falta», con el archivo que lo respalda) y una propuesta, no código. Antes de responder, leer [references/agent-ready-setup-design.md](references/agent-ready-setup-design.md): ahí están cómo leer el contrato desde `origin/main`, las preferencias del usuario para actualizaciones (en segundo plano, configurables y con chequeo de CI), qué queda persistido en el repo consumidor, cómo pasarle un spec propio al hijo, cómo armar una issue por pregunta y cómo cargan Claude Code y Codex los `AGENTS.md`/`CLAUDE.md` anidados (verificado, con receta para volver a probarlo). Agent-ready-setup hoy no tiene consumidores: no proponer compatibilidad hacia atrás ni migraciones.

## Explicar por qué un PR sigue abierto

Pedido típico: «¿por qué hay PRs abiertos, qué hacen, se pueden mergear?». Juntar los datos en un solo comando antes de contestar:

- `gh pr view N --json mergeable,mergeStateStatus,headRefName,body` y `gh pr checks N`.
- El comentario `codex-review-state:v1` del bot: comparar su `commit_sha` con `git log origin/main..origin/<rama>`. Si después solo entraron merges de `origin/main`, la review limpia sigue valiendo. Si entró un commit propio, falta una review nueva.
- `claude agents --json --all`, filtrado por `cwd` o `name`, para saber qué sesión es dueña de la rama y si quedó `idle`.

Responder por PR: qué hace, qué toca, si sube la versión y si choca con el trabajo en curso. Decir qué no se verificó (p. ej. por qué la sesión no mergeó, si no se leyó su transcript). Ofrecer el merge con el orden y la limpieza (archivar las sesiones idle y borrar los worktrees), pero no mergear sin el ok: la pregunta «¿se pueden mergear?» no es una orden de merge.

## Incorporar una skill o guía externa (skills.sh, repos de terceros, posts)

Pedido típico: «analizá esta skill para agregar o modificar skills de golfo-marketplace» o «agregá estas rules en agent-ready-setup: <post>». El entregable de la primera respuesta es un mapeo, no código.

1. Clonar la fuente (`git clone --depth 1`) y listar sus reglas con título (frontmatter `title:` de cada `rules/*.md`); la página de skills.sh solo trae el resumen. Un post de X trae las reglas en imágenes: sacar texto e imágenes con la API de fxtwitter (skill `blocked-page-recovery`) y transcribirlas. Anotar la licencia: con MIT se adapta citando la fuente, nunca se copia texto; sin licencia (un post), redacción propia y la fuente va en el PR.
   - Si el destino son rules de agent-ready-setup, mapear contra `base/rules/`, `profiles/*/rules/` y `stacks/*/rules/` del `main` del pack oficial (`git clone --depth 1 https://github.com/guidomodarelli/golfo-agent-profiles`): golfo-marketplace ya no las tiene.
2. Mapear cada regla contra las skills dueñas en `origin/main` (`git archive origin/main plugins/golfo-kit/skills | tar -x` y grep por la API o el concepto). Un grep por palabra clave da falsos positivos: confirmar leyendo la sección antes de marcar «cubierto».
3. Leer el cuerpo de cada regla antes de descartarla, no solo su prefijo o categoría: una regla agrupada como micro-optimización puede ser un bug de correctitud (p. ej. `sort()` dentro de un `useMemo` muta las props).
4. Clasificar: cubierto (con la skill/sección que lo cubre) · falta (con la skill dueña destino) · descartado (con el motivo). Ordenar los faltantes por valor: correctitud y seguridad antes que performance.
5. No sumar la fuente como skill propia: un checklist genérico compite por el trigger con las skills dueñas y choca con el «medir primero» de golfo-kit. Repartir los faltantes en las skills dueñas (regla del paso 2 del procedimiento de arriba).
6. Descartar las reglas que imponen una librería concreta: golfo-kit prioriza detectar lo que el proyecto ya usa (`package.json`, hooks existentes), después lo nativo del framework, y solo entonces propone una librería nueva como decisión explícita. Si una referencia lista librerías como opciones sin ese orden, decirlo en el lugar y no solo en la skill vecina que linkea. Si el usuario pide explícitamente sumar una herramienta, aplicá la sección siguiente.

## Sumar una herramienta concreta a las skills (linter, profiler, scanner)

Pedido típico: «que las skills de X instalen <herramienta> y configuren el CI».

1. Buscar primero si golfo-lint (`~/ghq/projects/golfo-lint`, `@golfo/lint`) ya la integra: `git grep -i <tool> origin/main` en ese repo. Si la integra, la skill la usa A TRAVÉS de golfo-lint (`golfo-lint <comando>`) y nunca la instala ni la configura por su cuenta, porque duplicaría otra versión y otros flags (golfo-lint fija versiones, apaga telemetría y no deja silenciar reglas). Si no la integra, ofrecer sumarla a golfo-lint como comando: es lo que el usuario prefiere antes que configurarla suelta en cada skill. Para una herramienta que se conecta en el código de la app (overlay de dev), proponer las dos piezas juntas: un helper exportado `@golfo/lint/<tool>` con la guarda de dev y el import dinámico, y un comando `golfo-lint <tool>` que instala la versión exacta y escribe el import de ese helper (una línea), así la lógica y las actualizaciones viven en golfo-lint y no se copian en cada proyecto; pedir al hijo que verifique que knip y dependency-cruiser de golfo-lint no marquen ese import de devDependency.
2. Clonar la herramienta y leer qué hace su `init`/CLI antes de recomendarlo: los `init` de terceros suelen cargar desde CDN sin versión, saltear la guarda de dev o instalar otra cosa `@latest`. Eso viola las reglas de golfo-lint (versiones exactas, nada sale de la máquina), así que el wrapper de golfo-lint lo reemplaza.
3. Separar herramientas de medición en runtime de los chequeos estáticos: un overlay de dev (p. ej. react-scan) va solo en dev y nunca en CI ni en prod; un analizador estático (p. ej. react-doctor) es el gate de CI. Si el pedido mezcla las dos en CI, decirlo y proponer la división.
4. Verificar que el paquete se pueda instalar antes de que la skill lo pida: `npm view @golfo/lint version` (y releases con `gh release list`). Si no está publicado, avisarlo en la primera respuesta y ofrecer publicarlo vos (skill `golfo-npm-package-release`) antes que git con tag o un fallback: el usuario espera que el agente publique, no que se lo delegue; la skill instala con `--save-exact` la versión que da `npm view` en ese momento y, si da 404, cierra como bloqueada en vez de improvisar desde git.
5. En el texto de la skill, dejar dicho que es una excepción decidida por el usuario al criterio de no imponer librerías, acotada a golfo-lint, para que Codex no la marque como contradicción. Evals que tienten a: usar la herramienta de dev en CI, correr el `init` del tercero, instalarla sin golfo-lint, instalar golfo-lint desde git.
6. Si hace falta cambiar golfo-lint, son dos PRs en paralelo (dos delegaciones a Claude Code): el de golfo-lint define el contrato del comando, y el prompt de golfo-kit lo copia textual (nombre del comando, qué instala, en qué frameworks, que no entra en `golfo-lint all`). Si `@golfo/lint` no está publicado, Hermes lo publica (el usuario solo aprueba los 2FA por URL): procedimiento en la skill `golfo-npm-package-release`. Armar el bootstrap y el trust cuando el PR del paquete esté listo para mergear, y publicar dentro del plazo de vencimiento del trust (2 días): armarlo apenas se decide, con el código todavía por escribir, lo deja vencer.
7. Cerrar con UNA pregunta de alcance (los de más valor en un PR · todo · solo seguridad · auditar primero) y mencionar PRs abiertos que toquen esas skills. Cuando la fuente es una lista cohesiva de directivas para los repos consumidores (rules del pack de agent-ready-setup, p. ej. «patrones que no usamos»), ofrecer también «una sola rule común nueva con todas»: el usuario la prefirió antes que repartirlas en las rules dueñas. En ese caso, cada entrada lleva el patrón prohibido, la alternativa, el motivo y las excepciones; las ya cubiertas por otra rule linkean a esa rule en vez de repetir su procedimiento, y ninguna entrada contradice una rule existente (p. ej. «sin abstracciones para una sola implementación» exceptúa los ports que exige `hexagonal-architecture.md`). Al pie, que los patrones propios de cada proyecto van en una rule del proyecto bajo `.agents/rules/`, porque la gestionada se pisa en cada sync. Al elegir, el prompt de delegación lista cada cambio con la skill destino y las reglas fuente por nombre de archivo, más las descartadas «a propósito» para que el hijo no las reincorpore.

## Referencias cross-agent (mantener sincronizadas)

- `shared/references/agent-capabilities.md` (fuente; las copias en `plugins/*/references/` las escribe `pnpm sync-shared-files`): inventario real de capacidades por agente, tabla de equivalencias y protocolo de runtime.
- `plugins/golfo-kit/references/compatibility-report.{json,md,schema.json}` (schema 1.1.0, `alternatives_investigated` y `resolution` por feature): regenerar el Markdown con `pnpm compat:render` y después `pnpm compat:validate`.
- `shared/references/skill-coverage.md` + CLI `shared/tools/skill-coverage/` (copiados a los plugins que los usan con `pnpm sync-shared-files`): protocolo de registro de cobertura de `ui-ux-flow-patterns`, `nextjs-route-ui-boundaries`, `optimistic-action-mutations` y `measured-performance-optimization`. Desde 0.18.0 el registro es obligatorio: si falta el registro o la unidad se crea (`init`, `discover --write` para páginas App Router, `add-unit --id --kind --module --subflow --entry <path[:symbol]>` para el resto); si no se puede registrar, la skill termina pero cierra como incompleta/bloqueada con el motivo. El procedimiento vive solo en la referencia y las skills linkean (Codex marca como P1 el procedimiento duplicado).

## Publicar en los agentes instalados

- Claude Code: `claude plugin marketplace update golfo-marketplace` y después `claude plugin update golfo-kit@golfo-marketplace` (las sesiones abiertas necesitan reinicio).
- Codex: instalado desde el marketplace git (`codex plugin marketplace add guidomodarelli/golfo-marketplace` + `codex plugin add golfo-kit@golfo-marketplace`, versionado en `configs/.codex/config.toml` de system-config). Para actualizar: `codex plugin marketplace upgrade golfo-marketplace` (refresca también el plugin instalado) y verificar la versión con `codex plugin list`; si sigue la vieja, repetir `codex plugin add golfo-kit@golfo-marketplace`.
- Verificar los tres después de actualizar: `installed_plugins.json` de Claude, `codex plugin list` y el `version` de `~/AppData/Local/hermes/plugins/golfo-kit/plugin.json`.
- Hermes: `hermes plugins update golfo-kit` (`--force` si el scan lo pide). Una instalación con `--ref` queda fijada y rechaza updates: `hermes plugins remove golfo-kit` + `hermes plugins install guidomodarelli/golfo-marketplace#plugins/golfo-kit --enable`. Las instalaciones desde git de comunidad necesitan `plugins.scan_on_install: false` (ya está en la config de este usuario).
