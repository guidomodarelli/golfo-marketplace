# Reglas del repo y gotchas que moldean el flujo

Leer antes de commitear, pushear, subir una versión, mergear o tocar un `SKILL.md`, un script de agent-ready-setup o un job de CI.

- Todo PR que toque `plugins/<p>/` sube la versión, y los tres manifests coinciden: `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json` y el `plugin.json` portable (Agent Plugins v1, el que usa Hermes). `pnpm create-version golfo-kit --bump <patch|minor>` actualiza los tres, pero commitea solo los manifests y pushea sin force: commitear antes el cambio de contenido, y después de un rebase subir a mano. `pnpm check-version-bump` compara contra el merge-base y pasa aunque `origin/main` ya haya superado la versión del PR: antes de pushear, `git fetch` y comparar con `git show origin/main:plugins/golfo-kit/plugin.json`; si main la superó, rebasar y subir a la patch siguiente.
- Cambios fuera de `plugins/` que no tocan una skill (`AGENTS.md`, `README.md`, scripts del repo): no llevan bump ni pasan por `/skill-creator`, así que Hermes los hace directo en un worktree. Las skills fuera de `plugins/` (`.agents/skills/`, como esta, y `skills/`) tampoco llevan bump, pero cualquier cambio bajo su directorio sí sigue las reglas 1, 2, 4 y 5 del `AGENTS.md` (`/skill-creator`, evals y `/skill-optimizer mode=audit`). Igual cierran con PR (`pr-description-template`) y el loop de Codex delegado en una sesión de Claude Code.
- Frontmatter: todo `SKILL.md` sigue la especificación de Agent Skills (regla del `AGENTS.md`; ahí están los límites). `pnpm validate-portable-plugins` solo chequea `name` y `description`. Para auditar el resto (`metadata` con valores no string, `compatibility` > 500), parsear los frontmatters de todos los `SKILL.md` con PyYAML (`yaml.safe_load`) en vez de grep: las plantillas anidadas en `assets/` de agent-ready-setup también son `SKILL.md` y cuentan.
- Un `SKILL.md` anidado dentro de una skill (ejemplos, fixtures, packs de prueba) va solo bajo `assets/`, `references/`, `templates/` o `scripts/`: Hermes recorre el plugin instalado de forma recursiva y solo poda esas cuatro carpetas, así que uno bajo `examples/` u otra carpeta se instala como skill real en la máquina del usuario. Después de publicar una versión, revisar que no aparezcan skills nuevas inesperadas en Hermes.
- Gates de CI: `pnpm validate-portable-plugins` (Hermes descarta en silencio la skill que rompe `name` o `description`; una `description` con `: ` sin comillas rompe el YAML), `pnpm compat:validate` (compatibility report JSON contra schema contra Markdown), `pnpm check-version-bump origin/main` y las suites bats.
- `.codex-autofix/` es estado local del loop (gitignored): nunca se commitea.
- El repo solo permite merge commits: mergear con `gh pr merge --merge` (squash y rebase fallan).
- PRs apilados: `gh pr merge --delete-branch` sobre la base cierra el PR que apunta a esa rama. Cambiar antes la base del PR de arriba a `main` (`gh pr edit <n> --base main`) y recién ahí mergear la base.
- Los scripts de agent-ready-setup corren también en Bash 3.2 (macOS del CI): `"${2:-{}}"` no da `{}` ahí; usar una variable local con el default. En ese Bash, un `[[ ]]` que falla no corta un test de bats: el job de macOS puede pasar con una aserción `[[ ]]` rota o reportar otra línea, así que una falla con `[[ ]]` se confirma en el log de Linux o Windows.
- Un job de CI que prueba agent-ready-setup clona la skill fuera del repo bajo prueba: sus `CLAUDE.md` anidados contarían como proxies del proyecto.
- El checkout principal lo comparten otras sesiones y puede estar en una rama ajena: trabajar en un worktree hermano desde `origin/main` y nunca cambiar la rama del principal.
- En Windows, `git worktree remove` del worktree que es el cwd de una sesión viva lo desregistra y lo vacía pero no borra la carpeta: borrarla (`rmdir`) después de cerrar la sesión.
- El `AGENTS.md` prohíbe subagentes salvo pedido explícito: un prompt de delegación aclara que los fixes van en el worktree, no en subagentes ni clones efímeros.
