# Diseñar capacidades nuevas de agent-ready-setup

Leer cuando el usuario pregunta «¿se puede hacer que agent-ready-setup tenga X?», pide una propuesta según lo que está hecho hoy o hace varias preguntas de roadmap con una issue por pregunta. El entregable de la primera respuesta es un diagnóstico y una propuesta, no código.

## Proponer una capacidad nueva (diseño, sin código)

1. Actualizar antes de opinar: `git fetch origin --prune`. Avanzar el checkout principal con `git merge --ff-only origin/main` solo si está en `main` y limpio, porque lo comparten otras sesiones. Leer la skill desde `origin/main` (`git archive origin/main plugins/golfo-kit/skills/agent-ready-setup | tar -x -C "$TMPDIR/ars"`) y no desde el checkout, que puede estar en una rama ajena. Esa skill es el motor: el contenido (catálogo, rules, skills de stack y template de `AGENTS.md`) está en el pack oficial `guidomodarelli/golfo-agent-profiles`, que se lee de su `main` (`git clone --depth 1`).
2. Leer primero el contrato: `agent-ready-pack.json` del pack oficial (catálogo: `kind` stack/capability, `requires`, `conflicts`, `tools`, `stackDefaults`, `detect`; los profiles de CI están en `assets/ci/profiles.json` del motor), `references/profiles-and-lockfile.md` (manifest y lockfile por repo, ownership, sección «Límites conocidos») y `references/managed-agents-block.md`. Para confirmar qué está implementado, grep en `scripts/agent-ready-state.py` (`load_profile_catalog`, `resolve_profiles`, `compose_stack_directory`). Muchos pedidos ya existen en parte, así que la respuesta arranca con «ya existe / falta», cada punto con el archivo que lo respalda.
3. Diseñar las extensiones sobre el contrato que ya existe, sin armar un mecanismo paralelo:
   - El lockfile registra lo nuevo (commit resuelto y digest), aunque la fuente siga una rama.
   - Una colisión de destino falla antes de escribir. Lo externo suma assets propios y nunca pisa uno gestionado.
   - El ownership y el retiro de assets se aplican igual que hoy.
   - Con `REVIEW_MODE` no se descarga ni se escribe nada.
   - Preferencia del usuario para actualizaciones: assets siempre al día, en segundo plano y sin bloquear la sesión (`run-detached.py` desde SessionStart), y todo configurable en el manifest con override por fuente (`updates` auto/pinned, `ref` a seguir, `ci` fail/warn/off). `--plan`/`--status` refrescan la caché por defecto (`--offline` para no tocar la red) y el CI clona las fuentes y falla si falta actualizar.
   - No diseñar compatibilidad hacia atrás (migraciones, alias, «los repos ya adoptados conservan su valor»): el usuario dejó dicho que agent-ready-setup no tiene consumidores, y esas piezas encarecen cada issue y cada PR. Si en el futuro aparece un consumidor real, volver a preguntar.
   - Principio del usuario para toda capacidad: «simple por defecto, configurable cuando hace falta». Cada funcionalidad tiene su `enabled` y opciones propias, con un default que anda con la configuración vacía; nada es obligatorio solo por existir, y sirve igual para un proyecto personal que para una empresa (lo corporativo, como listas de la organización, firmas o claves bloqueadas, es una capa opcional que no existe si no se configura). Proponer la configuración como schema único con los defaults adentro, capas defaults < organización < usuario < proyecto < flags/env, manifest disperso (el apply no escribe valores iguales al default) y `--plan` mostrando la capa de origen de cada valor. Defaults ya confirmados: detección encendida, updates `auto` en background, refresco de caché en plan/status, `ci: fail`.
   - Seguridad configurable sin imponer fricción: el único default que no se afloja es ejecutar código de una fuente ajena (instalar CLIs, correr scripts); rules y skills se aplican siempre. Ejecución automática y sin confirmaciones para fuentes confiables, con «quien agrega la fuente, la aprueba» en su máquina y el comando exacto para aprobar en el `--status` de los demás. El proyecto puede endurecer libremente; aflojar desde el manifest solo vale si la máquina aprobó ese repo, porque si no un PR podría apagar las validaciones y correr código en todas las máquinas. El usuario aprobó este modelo y descartó pedir confirmación por script.
   - Stacks y profiles conviven como un solo mecanismo: el stack es un rol (`kind: stack`) dentro de profiles, no un sistema aparte. Para ampliarlo, proponer capas con `requires` (runtime → framework → variante), nombres de assets propios por stack para poder combinarlos y un template base de `AGENTS.md` con una sección por stack, en vez de quitar el rol o sumar un catálogo paralelo.
   - El stack es opcional: un repo sin código (redacción legal, documentación) se configura solo con capabilities y el template base genérico. Por eso las rules de desarrollo van en la capability `software-development` (`profiles/software-development/` del pack) que los stacks traen por `defaults`, y la base (`base/`) queda como núcleo que sirve en cualquier repo. Las tecnologías propias se cubren con capas de stack o stacks primarios en packs externos, detectables por estructura de carpetas.
   - Versiones para soluciones entregadas a clientes: fijar el CONTENIDO (la fuente `golfo`, el pack de contenido, con `ref` y `updates`), nunca el motor. El motor es el plugin instalado, uno por máquina, y se actualiza siempre; la compatibilidad se declara solo con un mínimo (`minEngine` + `schemaVersion`), sin tope superior. Actualización controlada por fuente, no por archivo (medio pack deja combinaciones que nadie probó), con plan previo que muestra versión, changelog, cambios incompatibles, diffs y contradicciones de contenido en las dos direcciones (rule gestionada nueva contra una propia, y rule propia nueva contra una gestionada), solo como reporte y con `block` opcional. Un preset «entregado» lo deja todo `pinned` y aplica desde el lock.
   - El chequeo de CI es un comando común de la skill, independiente del proveedor (hay organizaciones con Jenkins sin GitHub Actions): códigos de salida estables, `--format json`, auth de fuentes privadas solo por git, `ci: off` para apagarlo, y ningún workflow proyectado sin pedido. La configuración guiada pregunta una sola vez, con el proveedor detectado primero, y nunca en modo no interactivo (SessionStart, background, review, CI).
   - Conflictos entre lo que se compone (rules, skills, MCP, CLIs, hooks, permisos, niveles de instrucciones, providers): separar tres clases, porque solo una es un problema de verdad. Duro (mismo nombre o destino con distinta configuración): falla antes de escribir. Complementario (se activan juntos y cada uno resuelve una parte distinta, como detectar y arreglar, o Playwright y DevTools): no avisa. Competidor (mismo trabajo de formas distintas, así que el agente elige al azar): avisa con el par y en qué difieren. Dar una forma de declararlo (`complements`, `overrides`) en vez de depender solo de la heurística. Para MCP, clasificar con metadatos declarados (`provides`), porque listar sus tools implica arrancar el servidor, o sea ejecutar código; y no registrar en el proyecto un servidor que el usuario ya tiene a nivel usuario. Incluir siempre «rules contra la realidad del repo» (la rule pide Vitest y `package.json` tiene Jest), que se detecta con las señales estáticas de `detect`.
   - Cuándo se detectan: no solo ante una actualización. Al editar (extender el hook `check-harness-consistency.sh` que ya corre en `PostToolUse`), al iniciar sesión en background, en `--plan`/`--status`, en el apply y en CI. Lo estructural corre siempre porque es barato y determinista (`fail` en CI); lo semántico usa la revisión de IA cacheada y va apagado en CI por defecto, porque necesita la CLI de un provider con credenciales ahí.
   - Toda revisión de IA (consistencia al editar, `AGENTS.md`, conflictos) pasa por una caché común y granular: unidad chica (archivo, par de rules, rule contra config), clave = hash del contenido + versión del chequeo + modelo + motor, y guarda el resultado, no solo «ya se revisó», para mostrar hallazgos sin llamar al provider. La caché es local (`.git/info/`, compartida por los worktrees); las decisiones del equipo van aparte y versionadas: aceptar o descartar un hallazgo individual por id con motivo obligatorio, con alcance `content` (vuelve a «a confirmar» si cambian sus líneas) o `pair`, sin silenciar los demás hallazgos del par. Una caché commiteada solo puede saltear una revisión con hash igual en CI, nunca dar un conflicto por resuelto, porque cualquiera la edita.
   - Aprendizaje y personalización por cliente: separar por ciclo de vida. Lo reutilizable (conocimiento del dominio, guardrails, defaults de estilo) va en un pack que mantiene el desarrollador; lo que el agente aprende de un cliente va en el repo del proyecto como rules y skills sueltas (no profiles: un profile es unidad de composición y distribución, se arma recién al promover); lo genérico se promueve al pack por PR explícito, y lo que aprenden dos o más clientes se propone para promover. Descartar el repo hermano para lo aprendido (el agente pushearía a otro repo en cada aprendizaje, `path:` no existe en otra máquina, `auto` lo propaga a todos). Recomendar mantener profiles y aprendizaje juntos con roles distintos: el profile es el piso, el aprendizaje la personalización; una preferencia aprendida REEMPLAZA la regla del profile (override desde el proyecto, una sola activa) en vez de sumarse, salvo las reglas que el profile marca como fijas; actualizar el profile no pisa lo que un cliente reemplazó. Aprender solo de mensajes del usuario, nunca del contenido de documentos (prompt injection), con un commit por aprendizaje y trailer `Learned-from:`.
   - Quién decide lo aprendido: el AGENTE, nunca el cliente (el usuario lo rechazó explícitamente; nada de «¿lo guardo?»). Reglas de evidencia: instrucción explícita persistente («siempre», «de ahora en más») se guarda ya; señal implícita queda candidata y se guarda sola al aparecer en dos episodios distintos; puntual o ambigua no se guarda; contra algo aprendido antes gana lo más reciente (`supersedes`); contra una rule de profile, `overrides`; contra un guardrail `locked`, no se guarda y se avisa en una línea. Reorganizar solo es automático si la revisión confirma que no cambia el comportamiento; borrar fuera de un reemplazo y promover los decide el desarrollador. La red de seguridad reemplaza a las preguntas: commit por cambio, log, `revert` y revisión del desarrollador en cada mantenimiento. Si proponés alguna pregunta al cliente, que sea sobre su trabajo («¿en todas las actas o solo en esta?»), acotada y apagable, y ofrecela como opción, no como default.
   - Registro: candidatos con forma canónica + evidencia (sesión, fecha, cita literal), comparados con la caché de revisiones; se cuentan episodios distintos, no mensajes; vencen sin evidencia nueva. Índice de aprendidos con `supersedes`. Historial = git (trailers) + log legible append-only. Las citas pueden tener datos del caso: el `harvest` entre repos lee solo las formas canónicas. Hooks útiles al estilo Engram: revisión de los mensajes del usuario al cerrar el episodio (solo suma candidatos) y resumen sin modelo al iniciar. Reorganizar al cerrar el episodio, con intervalo mínimo, nunca a mitad de tarea.
   - Episodios en vez de sesiones (un cliente puede usar siempre el mismo chat): la evidencia se cuenta por episodio, que es nuevo con otra sesión, otro día local o `learning.episodeGapHours` (4 por defecto) sin mensajes. Las horas se cuentan sin procesos vivos: el hook del prompt del usuario guarda `lastUserMessageAt` por `session_id` en un archivo local de `.git/info/` y el corte se calcula al llegar el próximo mensaje. Un episodio abandonado igual tiene que cerrarse, así que sumar siempre un reloj fijo, en tres capas: hook de fin de sesión, barrido desde cualquier hook del repo y un timer del planificador del sistema que corre `agent-ready learn sweep` (chequeo barato; IA solo si hay algo que cerrar). El timer es una tarea DE USUARIO (schtasks sin `SYSTEM`, LaunchAgent, crontab o `systemd --user`): no pide admin, y si una política lo bloquea el apply no falla y `status`/`doctor` lo informan.
   - Rules atómicas: la unidad es la rule con `id` estable dentro de un archivo agrupado por tema (no un archivo por rule), con metadatos en un comentario HTML. Una `key` de decisión hace deterministas los conflictos (dos rules activas con la misma `key` = conflicto, sin IA: «Jest vs Vitest») y el upsert del aprendizaje; hash por rule para idempotencia; `overrides`, `locked`, caché, plan y revert por rule; grafo de impacto (`requires`, overrides, skills que la citan, harvest). Las excepciones van pegadas a su rule y no se atomizan, porque sin ellas el modelo la sobreaplica.
   - Antes de proponer un umbral numérico (largo máximo, cantidades), medirlo contra el corpus real (p. ej. los bullets del pack: mediana y percentiles) y proponer dos niveles, aviso y falla, configurables: un número inventado deja afuera la mitad del contenido y el usuario lo cuestiona.
   - Equipos en un mismo repo (estudio con varios profesionales que no saben git): el motor es un comando `agent-ready sync` disparado por timer, inicio de sesión y cada escritura (commit, fetch, integrar, push con reintento, cola offline, nunca force, modo PR si la rama está protegida), no git hooks ni Husky, que solo se disparan con operaciones de git o necesitan Node. Los hooks de git sirven solo como merge drivers por rule, por id y append-only. Cada aprendizaje es personal (carpeta por usuario, solo se carga para él) o de equipo; el alcance dudoso se resuelve con la pregunta de alcance y, sin respuesta, queda personal; lo que aprenden N personas se promueve a equipo en cada sync con id determinista. La identidad es local por usuario del sistema operativo (archivo en `~/.config`, `identity link` entre máquinas), no la cuenta de git (puede ser compartida) ni el hardware. Documentos: el agente trabaja siempre en Markdown y genera los PDF (no versionados); PDF o Word del usuario son solo entrada inmutable con su `.md` extraído al lado.
   - Los conflictos de contenido que no se resuelven solos llegan al USUARIO FINAL, no al desarrollador (no escala con muchos clientes): el agente le explica en palabras simples, sin términos de git, quién cambió qué, cuándo y en qué difieren, y ofrece conservar uno, el otro o fusionar (mostrando la fusión antes de guardarla). Decide el primero que abre sesión y queda en el log. El desarrollador aparece solo para fallas que no son de contenido (credenciales), vía `doctor`. Nunca dejar el repo a medio mergear.
   - Varios clientes en repos distintos: nada sale solo de un repo; el desarrollador corre `harvest` sobre sus clones (participación activa por defecto con opt-out por repo, decisión del usuario), con texto generalizado sin datos del cliente.
   - Memoria de hechos (personas, expedientes, decisiones de un caso) es de Engram, no del aprendizaje: capability activa por defecto que NUNCA exporta al repo (secreto profesional; `.engram/` ignorado y `check` falla si está versionado) y NUNCA entra en el `harvest`. Una instrucción persistente va al aprendizaje y no a Engram, para no duplicarla ni dejar memoria vieja que contradiga una rule.
4. Lo específico de una empresa o tecnología in-house nunca entra en el pack oficial ni en golfo-kit, que son públicos. Las opciones son una rule del proyecto en `.agents/rules/` o una fuente externa versionada. Seguir una rama en `auto` hace que quien pushee a la fuente cambie las instrucciones del agente en todos los consumidores: decirlo una vez como riesgo y documentarlo, con el diff del lock y el chequeo de CI como control, en vez de prohibirlo, porque el usuario eligió actualizaciones automáticas.
5. Si se detectan capabilities, `plan` las sugiere y el apply no las aplica solo. Solo el stack primario se aplica por detección, porque una capability aplicada por una heurística le cambia el comportamiento al agente sin que nadie la haya pedido.
6. Proponer PRs chicos en orden de dependencia y decir qué no harías y por qué. Cerrar con preguntas numeradas con letras (alcance · variantes de diseño · spec primero en `docs/specs/`) y nombrar los PRs abiertos que tocan la skill (`gh pr list` + `gh pr diff N --name-only`).
7. Decir qué queda persistido en el repo consumidor. Una fuente externa proyecta sus assets como copias gestionadas y commiteadas: rules, skills y vistas `.claude/`, más el manifest con la fuente y el lock con el commit y los digests. El agente las lee sin acceso a la fuente; actualizar o verificar sí la necesita. Si no se aclara, el usuario lo pregunta después, porque define si el diseño le sirve.
8. Si el usuario responde con un spec propio (contratos y criterios de aceptación), ese spec es el contrato. Guardarlo en el scratch y pasarle la ruta al hijo de Claude Code con «leelo entero antes de empezar: manda sobre este prompt», sin parafrasearlo, porque un resumen pierde contratos. Revisar si la exportación desordenó columnas de tablas y avisárselo al hijo. Si un PR depende de otro, el segundo va stacked sobre la rama del primero (skill `stacked-pr`). Un cambio de alcance posterior se manda al hijo enseguida, diciendo qué partes del spec reemplaza.
9. «Seguí con los PRs» sobre un roadmap de issues: una sola sesión de Claude Code que las implementa en el orden de la sección de orden, un PR por issue, y arranca la siguiente recién después del merge de la anterior (rebase sobre `main`), para no apilar diez PRs que se rebasan en cadena. Cada issue es el spec: el hijo la lee entera, con comentarios, antes de empezarla, así que corregir la issue alcanza para lo que todavía no empezó; lo que ya está en curso se le manda por steering. Una issue NUEVA sí necesita steering aunque no haya empezado, con el orden completo actualizado: el hijo sigue la lista fija de su prompt y no ve issues que no le nombraron. Un bug en algo ya publicado (p. ej. una skill que aparece instalada sin querer) se le manda como prioridad: PR chico aparte antes de seguir el roadmap, y al mergear se actualizan los agentes instalados. Que frene con `blocked` antes de decisiones de producto que la issue no resuelve (crear un repo nuevo: nombre y visibilidad) y decida solo lo de bajo riesgo anotándolo en el PR.

## Preguntas de roadmap con una issue por pregunta

1. Contestar cada pregunta con el código de `origin/main`, nombrando la estrategia actual y el archivo que la implementa, antes de proponer. Un «no se gestiona hoy» se confirma leyendo la función, no por ausencia en un grep.
2. Una issue por pregunta en golfo-marketplace con la plantilla de `create-issue`: título en inglés con prefijo `feat:`/`refactor:`, cuerpo en español, etiqueta `enhancement`. Escribir los cuerpos en el scratch y crearlas con `gh issue create --body-file`.
3. Crearlas en orden de dependencia y linkearlas por número (placeholder en el cuerpo + `sed` con el número que devolvió la anterior). Lo que la propuesta necesita y hoy queda fuera de alcance de otra pieza (p. ej. stacks externos para mover las rules a un pack) va DENTRO del alcance de la issue, con su tarea y su criterio de aceptación, no como «prerrequisito» suelto: el usuario lo pidió así. Nombrar los PRs en curso de los que depende sin atribuirle a un número de PR un contenido que no es suyo.
4. Si una propuesta depende de cómo Claude Code o Codex cargan instrucciones, verificarlo antes de afirmarlo (sección siguiente) y dejar los hallazgos como comentario en la issue con links a la doc oficial.
5. Si el roadmap tiene una issue de seguimiento (tracking, con «Cómo mantener esta issue»), el orden vive SOLO ahí: no agregar secciones de orden en cada issue. Una issue nueva lleva la label del área, se cuelga como sub-issue (`id=$(gh api repos/<o>/<r>/issues/<n> --jq .id)` + `gh api -X POST repos/<o>/<r>/issues/<tracking>/sub_issues -F sub_issue_id=$id`), suma una sección `## 🔗 Dependencias` que enlaza a la de seguimiento, y la de seguimiento recibe la línea en su sección de orden. Leer sus reglas comunes antes de escribir (p. ej. «el contenido va al pack oficial» parte la issue en un PR del pack y otro del motor). Sin issue de seguimiento: cada issue termina con una sección `## 🗺️ Orden recomendado`: la secuencia completa (incluidos los PRs en curso), la propia marcada con «← **esta issue**» y una línea «Por qué en este lugar» con sus dependencias. Si el usuario acepta mover alcance de una issue a otra, editar las dos (descripción, criterios y tareas) y actualizar la línea del orden en todas. Al sumar una issue nueva al roadmap, regenerar la sección en TODAS desde una sola lista en Python (cortar desde `\n---\n\n## 🗺️ Orden recomendado` y volver a agregarla), no a mano issue por issue.
   - Un principio que el usuario fija para todo el roadmap (sin compatibilidad hacia atrás, todo configurable) va como nota `> **…:**` al principio de la descripción de cada issue, y también se le manda al hijo que implementa los PRs en curso.
   - En las issues, cada operación nueva para personas o agentes (aprobar fuentes, aceptar hallazgos, fijar versiones, configurar CI, ver la configuración efectiva) va como subcomando del CLI `agent-ready` que el usuario pidió para todos los flujos (`agent-ready <área> <acción>`), no como un flag suelto de `scripts/bootstrap.sh`. Decir siempre si ese subcomando ya existe en `origin/main` o es propuesta: presentar un comando que no existe como si existiera hace que el usuario pregunte si se creó. El CLI es una capa fina que delega en el motor; el paquete npm que lo pone en el PATH resuelve el motor del plugin instalado (o el fijado por el lock), nunca trae una segunda copia.
6. Editar issues ya creadas: bajar el cuerpo con una redirección de bash (`gh api repos/<owner>/<repo>/issues/N --jq .body > f`) o con `subprocess` en binario, editarlo en Python, escribirlo con `newline="\n"` y subirlo con `gh issue edit N --body-file f`. Después confirmar que no quedaron `\r` (`gh api ... --jq .body | tr -cd '\r' | wc -c` da 0). Si el cuerpo pasa por la salida capturada de `terminal()`, vuelve con CRLF, y al escribirlo en modo texto queda `\r\r\n`: GitHub lo muestra con líneas en blanco de más y rompe las tablas. Para reparar uno roto, sacar todos los `\r` y volver a subirlo.
   - Cuando el usuario invierte una decisión (p. ej. «el cliente no decide nada» después de diseñar confirmaciones), reemplazar la sección entera y después buscar en TODO el cuerpo con regex la palabra clave de lo viejo (`pregunt`, `confirm`) antes de subir: la política vieja suele sobrevivir en criterios de aceptación, tareas y secciones vecinas (hooks, reorganización), y la issue queda contradiciéndose. Asegurate con `assert old in body` antes de cada `replace`, para que un reemplazo que no encontró su texto falle en vez de pasar en silencio.

## Cómo cargan las instrucciones Claude Code y Codex (verificado)

Leer la doc en Markdown agregando `.md` a la URL (`https://code.claude.com/docs/en/memory.md`, `https://developers.openai.com/codex/guides/agents-md.md`) con `curl`: `web_extract` devuelve solo los primeros ~3 KB de esas páginas.

- **Claude Code:** carga `CLAUDE.md` del cwd y los de arriba al iniciar; los de subdirectorios a demanda, al leer, escribir o editar un archivo de ahí. Lee `AGENTS.md` nativo (desde v2.1.277) solo si NO hay `CLAUDE.md`, `.claude/CLAUDE.md` ni `CLAUDE.local.md` en el cwd o más arriba; nunca lee `AGENTS.override.md`, `AGENTS.local.md` ni nada bajo `.agents/`. El modo (`instructionFiles`) no se puede fijar desde los settings del proyecto.
  - Consecuencia: como agent-ready-setup deja un `CLAUDE.md` proxy en la raíz, cada `AGENTS.md` anidado necesita su `CLAUDE.md` proxy al lado o Claude no lo carga. No proponer sacar los proxies.
- **Codex:** arma la cadena una vez al iniciar, de la raíz git al cwd, un archivo por directorio, tope combinado `project_doc_max_bytes` (32 KiB). No carga los anidados por debajo del cwd; el modelo a veces los busca solo al tocar un archivo ahí, pero no está garantizado. La review de Codex en GitHub usa el `AGENTS.md` más cercano al código.
  - Consecuencia: para que Codex vea un bloque anidado de forma determinista, indexarlo desde el bloque gestionado de la raíz, contando ese texto contra el tope de 32 KiB.
- **Probarlo** cuando la doc no alcance: repo temporal en `$LOCALAPPDATA/Temp` con un token único por archivo (`ROOT_TOKEN_…` en la raíz, `NESTED_TOKEN_…` en `web/app/AGENTS.md`). Codex: `codex exec --sandbox read-only` desde la raíz y grep del token en el `.jsonl` más nuevo de `~/.codex/sessions`. Claude: `claude -p "Leé solo web/app/page.ts con Read…" --model sonnet --max-turns 4 --output-format json`, y grep del token en el transcript del `session_id`. Variar un solo factor por corrida (con y sin proxy anidado, sin `CLAUDE.md` raíz) y borrar los repos temporales al terminar.
